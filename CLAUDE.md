# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

«ЛингвоГерой» (LingvoHero): a game for children aged 6–9 to learn English (more languages later), built with React Native + Expo SDK 57 for Android/iOS. The mascot is Тим, a fox cub. The UI, hints and all docs are in **Russian**. Keep new user-facing text and project docs in Russian to match.

Key docs (Russian): [docs/CONTENT.md](docs/CONTENT.md) covers the content contract and publishing and matches the current implementation. [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) describes the _target_ system: a route or entity listed there may not exist yet. [docs/ROADMAP.md](docs/ROADMAP.md) tracks what is done. The admin web panel is specified in [docs/ADMIN_IMPLEMENTATION_PLAN.md](docs/ADMIN_IMPLEMENTATION_PLAN.md); stages A–D (auth, DB, manual editing, publishing, generation queue + OpenAI wizard) are implemented, E (backups, multi-publisher recovery) is not. Decisions are in [docs/adr/0001-admin-storage.md](docs/adr/0001-admin-storage.md) and [docs/adr/0002-generation-queue.md](docs/adr/0002-generation-queue.md).

## Commands

Requires Node ≥ 22.13 and pnpm 11.22.0. Run everything from the repo root.

```powershell
pnpm install --frozen-lockfile
pnpm dev            # Expo (mobile) — scan QR in Expo Go, or press `a` for Android emulator
pnpm dev:web        # Expo web preview at http://localhost:8081
pnpm dev:api        # Fastify catalog API at http://127.0.0.1:3001 (tsx watch); with DATABASE_URL also /v1/admin
pnpm dev:admin      # Vite admin panel at http://localhost:5173/admin/ (proxies /v1 to the API)
pnpm dev:worker     # generation worker (needs DATABASE_URL; GENERATION_PROVIDER=fake needs no OpenAI key)
# Learner accounts need ACCOUNT_SECRET in apps/api/.env; with ACCOUNT_MAIL_MODE=file the login codes land in .data/account-mail/
pnpm db:up          # PostgreSQL 17 via docker compose on port 5433 (5432 is taken on this machine)
pnpm db:migrate     # apply apps/api/drizzle migrations; regenerate with: pnpm --filter @lingvohero/api db:generate
pnpm admin:bootstrap <login>   # first admin; password from prompt or ADMIN_BOOTSTRAP_PASSWORD
pnpm admin:password <login>    # new password for an existing admin (prompt or ADMIN_NEW_PASSWORD), signs out its sessions; in the panel: «Пароль» under the menu
pnpm admin:import   # idempotent: content/store → editorial DB
pnpm admin:import-wardrobe [--generate]   # seed the bundled mascots/shop items; --generate queues bodies, slot maps and outfit layers

pnpm typecheck      # every workspace's tsc --noEmit + tsconfig.tools.json (scripts/, tests/)
pnpm test           # node:test via tsx: packages/learning-core/src/*.test.ts, apps/api/src/**/*.test.ts (no DB)
pnpm test:admin     # apps/api/src/**/*.dbtest.ts — needs DATABASE_URL_TEST + running DB; one throwaway database per test
pnpm format:check   # prettier (singleQuote, trailingComma all, printWidth 100)
pnpm test:e2e       # Playwright (first: pnpm exec playwright install chromium); panel.spec.ts skips without DATABASE_URL_TEST

pnpm content:publish content/<release>.json   # validate + publish a content release into content/store
node scripts/gen-image.js "prompt" out.png [1024x1024] [transparent] [low|medium|high]   # one-off artwork via OpenAI Images (key from apps/api/.env); use it whenever an image asset is needed; defaults to the API's image model so pictures match generated sets
pnpm --filter @lingvohero/mobile exec expo install --check
pnpm --filter @lingvohero/mobile exec expo export --platform all
```

To run a single unit test file, use `pnpm exec tsx --test packages/learning-core/src/course.test.ts`. Add `--test-name-pattern "<name>"` to run one test. For a single e2e test, use `pnpm test:e2e -g "<title>"`.

E2E starts its own servers on ports **8082** (Expo web) and **3002** (API, `scripts/e2e-api.ts`). The API serves a throwaway copy of `content/store` in `.cache/e2e-content`, so tests can publish without touching the real store; with `DATABASE_URL_TEST` it also creates the `lingvohero_e2e` database, imports that copy, enables the admin API (admin `admin` / `E2E_ADMIN_PASSWORD`, default `e2e-admin-pass`), the learner account API (file mail in `.cache/e2e-mail`; `tests/e2e/account-helper.ts` signs a fresh learner in) and runs an inline fake-provider worker. The app now requires a signed-in learner, so every app-level e2e starts with `signIn(page)`. Set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` to reuse a local Chromium. Screenshots go to `test-results/`.

For the native Android smoke test, run `python scripts/android-smoke.py --serial emulator-5554 [--course]`. It needs Metro running, an emulator with Expo Go and `ANDROID_HOME`, and it writes to `.cache/android-smoke`.

Env: `apps/mobile/.env` → `EXPO_PUBLIC_API_URL`. By default the app uses `localhost:3001` (or `10.0.2.2:3001` on the Android emulator). `apps/api/.env` → `HOST`/`PORT`. Use `HOST=0.0.0.0` for a physical phone. `OPENAI_API_KEY` is reserved but not used yet. Never put server secrets in `EXPO_PUBLIC_*`.

## Deployment and security

`docs/SECURITY_AUDIT.md` is the pre-deployment audit. The API refuses to start with `NODE_ENV=production` unless the configuration is safe (`productionProblems` in `apps/api/src/env.ts`: secure cookies, https origins, SMTP, no test database). `apps/api/.env.production.example` lists the server settings. Behind nginx set `TRUST_PROXY=127.0.0.1` (rate limits by client IP, IPv6 per /64; https Origin for the panel). Run `pnpm --filter @lingvohero/api start` and `worker:start` under systemd (both exit on an unhandled rejection). Security headers come from the API (`app.ts`), the panel gets a strict CSP. Generation has a per-job limit and `GENERATION_DAILY_LIMIT_USD` for all jobs together. `/v1/shop` is cached for 30 s (admin writes drop the cache), `/v1/shop-media` serves only published pictures.

## Account concept

One account belongs to one child with their own email address. Parents do not participate in the app. Family accounts, multiple child profiles per account and parental controls are outside the product scope. A profile is the child's own account data. Settings, progress and inventory belong to that account.

## Levels and mascot gallery

Implemented in `learning-core/src/levels.ts`, `api/src/account/progression.ts` and `mobile/app/friends.tsx`. The first lesson gives 100 XP; cumulative level thresholds are 0, 100, 300, 600, 1000, then +500. No repeat XP or extra level coins. Tim is always open; default unlocks are rabbit 3, bear 5, owl 8. The admin edits `unlockLevel`; server-owned `learner_mascots` grants persist and `PATCH /account/me` checks avatar access. Migration 0009 preserves existing selected mascots and old levels; `ACCOUNT_LEVEL_STEP` is now only the legacy migration setting. UI strings must cover ru/en/he. See [rules](docs/LEVELS_AND_MASCOTS.md).

## Architecture

pnpm workspace (`nodeLinker: hoisted`). The workspace packages export raw TypeScript source (`"exports": "./src/index.ts"`), so there is no build step for them.

- **`packages/contracts`**: Zod schemas are the single source of truth for data shapes. The current format lives in `src/course.ts` (schemaVersion 2): `courseLessonSchema`, `catalogSchema`, `releaseSchema`, `answerSchema` and `learningStateSchema`. Its `superRefine` checks enforce the cross-references: word→media, exercise→word, whether build-word tiles can actually spell the word (NFC code points), and catalog↔package consistency. `src/admin.ts` holds the deliberately lenient draft schemas (`lessonDocumentSchema`: empty arrays and empty strings allowed) and the panel's input/patch schemas; patch schemas are built from default-free fields because zod 4 `.partial()` keeps `.default()` values. `src/index.ts` also keeps the legacy v1 demo schemas, which are needed only for migrating old saves.
- **`packages/learning-core`**: pure game rules shared by the client and future server code. In `course.ts`, `assess()` grades an answer locally, `learn()` is the lesson state reducer (a wrong exercise is re-queued once at the end of the lesson, and drafts hold partial answers), `restoreLearningState` handles restore and `migrateDemo` moves v1 saves to v2. Rewards are granted once per lesson id, so a new lesson version never re-awards coins. `catalog.ts` holds `courseCards`/`reconcileCourseAccess`: courses (“сеты”) unlock sequentially within a language, and access once granted is never revoked. `index.ts` still has the legacy v1 `transition` reducer, which `lesson.test.ts` covers. `journal.ts` holds the pure rules behind the «Сокровищница» tab (daily quests, trophies, streaks) over a `Journal` (schema in contracts): `buildJournal` rebuilds it from verified lesson completions plus the coin ledger, `wallClock` maps UTC to the learner's calendar (`tzOffset` = minutes east of UTC). `shop.ts` is the stage-1 shop (coins only, per `../shop2` mockups): item catalog, a daily half-price deal rotating by calendar day, `buyItem`/chests and a streak-freeze booster that `protectStreak` spends automatically. **The server is the source of truth**: `apps/api/src/account/treasury.ts` rebuilds the journal on every read from `learner_attempts` (with `words`) and `learner_ledger` (quest claims, trophies, purchases, chest drops, spent freezes; `key` makes each grant idempotent) and writes auto-grants back; `/v1/account/treasury`, `/treasury/claim`, `/treasury/buy` lock the learner row. `AccountSnapshot.journal` comes with every `/me` and `/sync`; the mobile `DemoProvider` only extends it optimistically for unsynced lessons and calls the server to claim or buy. **Outfit**: `learning-core/src/outfit.ts` (`equip`/`unequip` one item per slot, `cleanOutfit`, `outfitLayers` sorted by `SLOT_Z`), stored as `learner_accounts.outfit` (`AccountProfile.outfit`, migration `0005`); `PATCH /v1/account/outfit` accepts only owned items in their own slot. `stats.ts` (`childStats`, `bestStreak`) feeds «Моя статистика» in the profile (`StatsCard`): words, lessons, stars, sets, streak and record, trophies, this week's lessons. The mobile `MascotStage` draws the body plus the pre-fitted layers from the shop catalog (portrait fallback when a mascot has no generated body); `app/wardrobe.tsx` is the «Примерочная» (try-on of unowned items, buy, «Сохранить образ»), the shop's «Надеть» saves immediately. Crystals, tickets and leagues are not implemented.
- **Mascots and the wardrobe as data (panel sections «Маскоты» and «Магазин»)**: tables `mascots`, `shop_items`, `outfit_layers` (`db/schema.ts`), admin routes in `admin/routes/wardrobe.ts`, public catalog `GET /v1/shop` + `/v1/shop-media/<sha>.png` (`shop-public.ts`, needs the DB). Creating a mascot (text description or an uploaded PNG) or an item (description or PNG, slot, rarity `common|magic|legendary`, price) queues an **asset job** on the same generation queue (`generation_jobs.kind` = `mascot|item`, `subject_id`, nullable `course_id`): stages `mascot-base` (transparent full body, 1024×1536, `images.edit` when there is a source picture), `mascot-portrait`, `mascot-slots` (vision call returning normalized boxes for head/eyes/outfit/back/companion, grown by `refineSlots`), `item-icon`, and `outfit-layer` per counterpart — the item painted onto that mascot's body through a slot mask (`maskPng`; `zoneFor`: headwear only gets the top of the head down to the eye line, clothes get the full width from the shoulders down so costumes can cover arms and legs, and the mask's top edge dips in the middle of the torso like a neckline (`Zone.neckline`, `zoneMaskPng`) — the model fills the mask to its edge, so a straight edge would show as a straight cut through the chest while a curved one reads as the garment's collar; beside the head box the zone climbs to the eye line so raised paws get whole sleeves) and aligns clothes on the head above the eye line (hands raised to chin height change between renders). Image models re-render the whole picture, so `generation/outfit-compose.ts` (over the tiny PNG codec in `generation/png.ts`) aligns the edit to the body by the untouched rows, measures drift outside the zone, keeps only the pixels the item added (diff mask; for hats and glasses additionally `keepNovel`, seeded only by pixels in the item icon's colours (`itemPalette` — the model swapped a rabbit's long ears for short ones under a hat, in colours the body lacks nearby): only pixels in colours the body does not have within ~45 px of them (a zone-wide palette threw away a gold crown on an owl with yellow tufts), plus changed pixels within ~5 px of those, then pieces under ~0.1% of the picture or under a tenth of the largest piece are dropped as stray strokes; a cape keeps the plain diff; clothes are delivered as a **whole-character picture** (`replaceBody`: the original head — the head box above the neckline, narrowing from the eye line to the neck width so raised paws come from one picture — on the model's body, blended along the border) that the app (`MascotStage`) and the panel (`Stage` with `replaces`) draw **instead of** the body, under every other layer (`SLOT_Z.outfit` is lowest); a covering layer could not hide what the model moved (a diff left the costume's boots mixed with the character's sneakers, a foot drawn aside left the original shoe sticking out). Clothes are checked by `seamDrift` along that border (limit 70; good edits score 53–64) instead of the head-drift check — the model redraws ears under a hat larger and elsewhere, and a plain diff turned them into a second pair; an item entirely in the body's colours falls back to the plain diff — 3 px grown, feathered) and rejects the edit as a retryable error when the character was redrawn or nothing was painted — the queue's three attempts pay for a fresh generation each time. `OPENAI_EDIT_MODEL` picks the edit model (empty = the image model; `gpt-image-1.5` with `input_fidelity: high` re-framed pictures far more than `gpt-image-2.5-flare` in practice). The edit prompt includes the mascot's own description: the masked part of the body is redrawn from the prompt, and without it the model dropped a t-shirt under a cape. Companions skip the edit (the icon is the layer). Logic in `worker/asset-stages.ts`; the provider gained `editImage` and image inputs for `generateText`; the fake provider returns fixed boxes. Only published mascots/items with assets reach the app. `pnpm admin:import-wardrobe [--generate]` seeds the four bundled mascots and five items. Accepted layers keep the model's raw edit as an asset too (`task.output.editAssetId`), so `tsx apps/api/src/cli/recut-layer.ts <mascot> <item> <edit sha256|asset id>` can rebuild a layer after a compositor change without calling the provider. The mobile app reads the catalog through `src/content/shop.ts` (cached, bundled fallback `DEFAULT_CATALOG` until something is published); learning-core's shop rules take the item list as a parameter (`shopItemsFrom`, `DEFAULT_SHOP_ITEMS`), and the server's `/treasury/buy` uses the published items. Item artwork in `apps/mobile/assets/images/shop/` was generated with `scripts/gen-image.js`.
- **`apps/api`**: Fastify. Public read-only content API (`/health`, `GET /v1/catalog?schemaVersion=2` with ETag, `/v1/lessons/:id/versions/:version`, `/v1/media/<sha256>.png|wav`) with `Access-Control-Allow-Origin: *` scoped to these routes only. The file-based store and `publishRelease()` live in `content.ts`. `buildApp({ contentRoot, admin?, adminDist? })` is injectable for tests; the admin plugin (`src/admin/plugin.ts`, prefix `/v1/admin`) is registered only when a DB is configured. Admin auth: scrypt passwords, session token hashed in `admin_sessions`, HttpOnly cookie `lh_admin`, `Origin` check on every non-GET (`src/admin/auth.ts`). Errors are `{code, message, fieldErrors?, requestId}` via `AdminError`/`parseInput` in `src/admin/errors.ts`. DB: Drizzle schema in `src/db/schema.ts`, SQL migrations in `apps/api/drizzle/` (generated; migrations reference `"public"."table"`, so test isolation is a database per run, not a schema). Publishing pipeline: `src/publishing/build-release.ts` (pure: rows → `Release`, lesson version = kept when `lessonHash` matches `last_published_hash`, else +1), `plan.ts` (immutable snapshot + diff + recovery of stuck `publishing` rows), `publish.ts` (copy draft media into the store, then the same `publishRelease`). Draft lesson documents reference media by `assetId`; `src/publishing/convert.ts` turns them into `CourseLesson` with `/v1/media/<sha>` paths and runs the strict schema.
- **Generation (stages C–D)**: `apps/api/src/generation/` holds the provider interface (`provider.ts`, `classifyError` → retryable/permanent), the OpenAI adapter (Responses API strict JSON schema, Images → PNG, TTS → WAV; SDK retries off, the queue retries), the deterministic `FakeProvider` (synthetic PNG/WAV, `input.simulate` failure injection — all tests use it), prompts (`PROMPT_VERSION` is part of every artifact hash; v2 asks for gender-neutral Russian — no «ты собрал»; target words define the whole vocabulary when there are at least two per lesson plus one, otherwise topic words fill it — `wordCountFor`), model DTO → draft mapping (`dto.ts`; the server assigns ids/tiles/order) and local review. `apps/api/src/worker/` is the Postgres queue: `queue.ts` (claim with `FOR UPDATE SKIP LOCKED`, 2-minute leases, backoff, cancel, retry = fresh 3-attempt budget for the task, its cancelled siblings and later stages), `stages.ts` (plan → text → review → media-plan → cover → image → audio → assemble; media tasks reuse a succeeded task with the same `input_hash`; the audio stage rejects near-silent speech as retryable (`wavPeak` in `admin/media.ts` — the TTS once returned zeros, and `inspectMedia` accepts any valid WAV; `tsx apps/api/src/cli/redo-speech.ts <lessonId> <wordId>` re-records one word in a draft lesson); `assemble` never overwrites a lesson whose `edit_revision` moved — it stores the AI variant — title, document and presentation — in `job.output.conflicts`, applied by `apply-conflicts`), `runner.ts` (`runWorkerLoop`, `runWorkerUntilIdle` for tests). Jobs are one per course at a time and idempotent by `idempotencyKey`; generation never publishes. A translated clone (`POST /v1/admin/courses/:id/clone`, `mode: 'translate'`) is the same kind of job with `input.source` set: `plan`/`text` translate the source vocabulary and adapt texts instead of inventing them, words carry the source picture (`GenerationWord.image`, atlas region included), and `media-plan` schedules audio only. `mode: 'copy'` duplicates lessons synchronously. A set's cover can be redrawn on its own: `POST /v1/admin/courses/:id/cover/generate {hint?, idempotencyKey}` (`admin/routes/cover.ts`) queues a `kind: 'cover'` job (with `course_id`, so it shares the one-job-per-set rule) whose single `course-cover` stage draws a 1536×1024 picture from the topic plus hint and sets it as the draft cover at once (edit revision +1; the old one stays in the library; the app sees it after the next release). The panel's cover field (`CourseForm` → `CoverGenerator`) shows it; `AssetPicker` takes the `selected` asset because the library lists only the newest 100 files.
- **Learner accounts (stage 4, written by a second agent)**: `apps/api/src/account/plugin.ts` is a separate Fastify plugin under `/v1/account`, registered only when `ACCOUNT_SECRET` is set. Passwordless: `POST /auth/code` mails a 6-digit code (HMAC of `challengeId:code` with the secret is stored, 10-minute expiry, 5 attempts; a new code cancels the older one; per email at most 8 mails an hour and 20 a day, and 15 wrong codes a day lock it until tomorrow; the old address is told when the email changes), `POST /auth/verify` creates the account on first login and issues a session (HttpOnly cookie `lh_learner` for browsers, bearer `token` for native clients — the response includes the token only when there is no `Origin`). Tables `learner_*` in `db/schema.ts` (migration `0002`). `POST /sync` replays each attempt's answer events through `learn()` from learning-core on the server, so stars and rewards (`learner_rewards`, one per user+lesson) cannot be forged; the server keeps the authoritative `LearningState` per user and a per-device `sequence` guards against stale uploads. Mail modes: `smtp`, `file` (dev: `.data/account-mail/<challengeId>.json` holds the code) or `disabled`. CORS for this plugin is an allow-list (`ACCOUNT_ORIGINS`), not `*`. Errors are `{code, message}` from the `FAULTS` table in `plugin.ts` (rejected sync attempts carry `code` too): the app shows `app.server.<code>` in the interface language (`serverText` in `src/account/api.ts`), older apps the Russian `message`; a new code needs a line in `texts/app.ts`. Mobile side: `apps/mobile/src/account/` (`AccountProvider` gates the app behind `AccountWelcome`, tokens in `expo-secure-store`), `DemoProvider` syncs attempts. `learn()` now records `events` and an optional `attemptId` in the session for this replay.
- **Interface language and lesson translations**: the app speaks ru/en/he (he is RTL). `apps/mobile/src/i18n/` holds `LocaleProvider` (above `AccountProvider`; device language by default, choice in AsyncStorage `lingvohero.locale` and `learner_accounts.ui_locale`), `useT()` → `t(key, params)` / `tn(key, n)` with per-locale plurals, and `texts/<section>.ts` files built with `defineTexts({ ru, en, he })`. Russian is the key source, so tsc reports a missing translation. Game data by id (quests, trophies, built-in goods, bundled mascots) goes through `i18n/content.ts` helpers. Lessons carry their own translations as an overlay `texts.en|he` (contracts `course.ts`; base fields stay Russian, `schemaVersion` stays 2); the catalog has `courses[].locales/texts`, `lessons[].titles`, `languages[].titles`. `localizeLesson`, `localizeCard`, `visibleCatalog` (`contracts/src/locales.ts`) are shared by the app and the server: a set not fully translated to the child's locale is hidden, also for `/sync` access checks (the device sends `locale`). The panel's «Перевести тексты» queues a `texts` job (`worker/text-stages.ts`: `lesson-texts` per lesson, `course-texts`); the course job queues one itself after `assemble`. `sourceHash` marks a translation stale when the Russian changes. Mascots and shop items have their own `texts` (migration `0008`): `POST /v1/admin/wardrobe/texts/generate` queues one `texts` job with `subject_id = 'wardrobe'` (stages `mascot-texts`, `item-texts`), manual edits in the panel's «Переводы» block are stamped as current, `/v1/shop` serves complete translations only, and the app's `mascotText`/`itemText` prefer them over the built-in dictionary. Learned-language words keep their own direction in RTL (`wordDirection`).
- **Several learning languages**: `learner_accounts.languages` (list) + `language` (current), migration `0007`. `PATCH /v1/account/me` takes any subset of `{name, avatar, language, languages, locale}` and finishes onboarding when name and avatar come together. The app: `LaunchGate` asks for a language after sign-up and, with several languages, at every cold start; the side menu (`react-native-drawer-layout`, ☰ `MenuButton` + swipe, off on /lesson and /result) links «Языки» (`app/languages.tsx`, `LanguagePicker`). `DemoProvider` exposes `catalog` (visible in the locale), `fullCatalog`, `languages`, `chooseLanguage`; languages added offline wait in its record and go with the next sync.
- **`apps/admin`**: React + Vite + react-router + TanStack Query, served at `/admin/` (Vite `base`). No React Native imports; the lesson preview (`features/preview`) runs `learn()`/`assess()` from learning-core against `GET /v1/admin/lessons/:id/preview`, which returns the built package plus `mediaUrls` for draft assets. `react`/`react-dom` are pinned to the mobile app's versions because of `nodeLinker: hoisted`.

Screens are in `app/`: the `(tabs)` group holds the home «Миры» (index), words, rewards and profile, and there are also `course.tsx` (lesson map, `/course?id=`), `lesson.tsx` and `result.tsx`. `src/state/DemoProvider.tsx` is the central store: it persists the `LearningState` under AsyncStorage key `lingvohero.learning.v2` and caches the catalog and packages per API URL. ### Content model and publishing

A **release** is a catalog plus a full set of lesson packages. `content/seed.json` is the initial release. The mobile app also **bundles** it (`client.ts` imports it) as a fallback when the API is unreachable. Bundled media is mapped by hand in `client.ts` to files under `apps/mobile/assets`. Server-only media is loaded from `${apiUrl}/v1/media/...`.

The rules below are enforced in `publishRelease` and the schemas:

- `content/store/` is the published store. It holds `catalog.json`, `catalogs/<rev>.json`, `lessons/<id>/<version>.json` and `media/<sha256>.<ext>`. **Never edit it by hand.** Lesson versions are immutable, and rewriting an existing version with different data is rejected.
- `catalog.revision` must increase with every publish. To change a lesson, bump its `version` in both the package and the catalog reference. Every release must contain every lesson it references.
- The catalog ref's `title`, `exerciseCount` and `requiredTypes` must match the package exactly. The mobile client re-checks this too.
- Media files are content-addressed by SHA-256, and the publisher verifies each hash and file signature (PNG/WAV). Validation of the whole release happens before anything is written. `catalog.json` is swapped last, via an atomic rename. A `.publish.lock` left behind by a crash must be removed manually, after checking that no publish is running.
- The app never gets original pictures. `preparePlan` and `/v1/shop` swap every image for a **delivery copy** (`admin/renditions.ts`, `sharp`): fitted into a `DELIVERY` box (cover 1024, word 384 per atlas cell, mascot body and layers 512×768, portrait 384, icon 320) and re-encoded as a 256-colour palette PNG, 10–20× smaller. Copies are made once per (asset, box), recorded in `asset_renditions` (so later releases keep lesson versions), hidden from the panel's library and stored as `source: 'rendition'` assets. Generation and the panel keep using the originals; panel previews use `/v1/admin/assets/:id/file?w=320|640`. `generation/png.ts` also decodes palette PNGs. Bundled artwork in `apps/mobile/assets/images` is pre-shrunk the same way; shrink any new picture before adding it (`shrinkPng`).
- An unfinished lesson session stores a full snapshot of its package version and stays on that version after catalog updates.
- A new exercise `type` requires an app update, because the client rejects unknown types during schema validation. New lessons, words, media or languages that use the existing mechanics (`listen-and-select`, `match-pairs`, `build-word`) are data only.
- Terminology: a “сет” (set) is `course` in code. Don't introduce a separate `set` entity. `previews` are «Скоро» (coming soon) placeholders that contain no lessons.
